# HCP Vault - HCP Terraform Secret Engine Demo

This project configures HashiCorp Vault to enable the Terraform Enterprise (TFE) secrets engine, specifically designed to securely manage and dispense dynamic HCP Terraform Team tokens. It also natively configures Vault JWT Authentication (OIDC) to enable zero-trust access directly from GitHub Actions workflows.

## What This Demo Demonstrates

This demo illustrates a secure, API-driven workflow where a GitHub Actions CI/CD pipeline dynamically requests access to an HCP Terraform workspace without relying on long-lived API tokens. By using HashiCorp Vault as an identity broker, GitHub Actions employs OIDC (JWT) to authenticate to Vault. Vault then securely generates an ephemeral HCP Terraform Team token via the Terraform Cloud secrets engine, strictly scoped to the repository's target workspace.

## Demo Components

- **GitHub Actions (Client):** The CI/CD pipeline orchestrating the infrastructure deployment. Provides its native OIDC token to authenticate to Vault.
- **HashiCorp Vault (Identity Broker & Secret Engine):** Validates the GitHub OIDC token, enforces the repository bounds, and leverages the TFE Secret Engine to generate short-lived credentials.
- **HCP Terraform (Target System):** The execution platform where the terraform workspace actually runs. Team access is dynamically created here by this module.

## Permissions

**Vault:**
Tokens executing this Terraform configuration require specific policies to configure the platform. The required capabilities include:
- **Namespace Access:** `create`, `read`, `update`, `delete` on `sys/namespaces/*` to manage sub-namespaces.
- **Secrets Engine Access:** `create`, `read`, `update`, `delete`, `sudo` on `sys/mounts/*` to enable and configure the secret engine.
- **Auth Method Access:** `create`, `read`, `update`, `delete`, `sudo` on `sys/auth/*` to enable and configure the JWT auth method.
- **Policy Access:** `create`, `read`, `update`, `delete` on `sys/policies/acl/*` to create and manage the GitHub Actions policies.
- **Role Access:** `create`, `read`, `update`, `delete` on the specific mount paths (e.g., `terraform/roles/*` and `auth/jwt/role/*`) to manage roles.

**HCP Terraform:**
The token provided via the `tfe_token` variable requires specific Organization-level API permissions. In the HCP Terraform platform UI, this corresponds to:
- **Manage Teams:** Required to create the TFE Team for the workflow.
- **Manage Workspaces:** Required to read the target workspace and assign `write` (plan/apply) Team Access grants to it.

## Authentications

### HashiCorp Vault

- **Static Token Authentication:**
  You can authenticate using a standard long-lived Vault token. Provide the token via the `VAULT_TOKEN` environment variable, alongside `VAULT_ADDR` and `VAULT_NAMESPACE`.
- **Dynamic Authentication:**
  You can authenticate using HCP Terraform's native Vault dynamic provider credentials (OIDC). This requires configuring `TFC_VAULT_PROVIDER_AUTH = "true"` and the associated Vault role environment variables in your workspace, allowing HCP Terraform to fetch short-lived Vault tokens automatically during runs.

### HCP Terraform (TFE Provider)

- **Static Token Authentication:**
  You can authenticate using a standard Organization, Team, or User API token. Provide this token string directly to the configuration via the `tfe_token` variable or locally via the `TFE_TOKEN` environment variable.
- **Dynamic Authentication:**
  You can authenticate dynamically leveraging Workload Identity (OIDC) or utilizing a Vault-injected dynamic token (such as the one generated in this demo pipeline). When using TFE Workload Identity, HCP Terraform natively fetches temporary TFE credentials via the `TFE_DYNAMIC_CREDENTIALS` configuration.

## Features

- **Dynamic TFE Secrets:** Creates a Vault Terraform Cloud Secrets Engine mount configured to securely proxy requests to the HCP Terraform API.
- **Automated Workflow Pipeline:** Automatically provisions an HCP Terraform Team matching the GitHub repository name, granting it `write` (plan/apply) access to the repository's target workspace.
- **GitHub Actions (JWT) Auth:** Establishes OIDC trust between Vault and GitHub, explicitly bounding claims so only authenticated runner workflows originating from the designated `owner/repo` can authenticate.
- **Strictly Scoped Engine Role:** Evaluates an auto-generated token extraction policy, mapping the authenticated Action to a dynamically provisioned token for its own workspace.

## Demo Value Proposition

- **Zero-Trust Security:** Trust is established dynamically via OIDC. No sensitive passwords or API keys are stored in GitHub repository secrets.
- **Ephemeral Credentials:** Team tokens generated by Vault are short-lived and automatically revoked, minimizing the risk of credential leakage.
- **Automated Isolation:** Each repository uses its own auto-generated Team ID, ensuring blast radiuses are strictly limited to single target workspaces.
- **Centralized Identity Management:** Vault bridges the gap between GitHub's identity and HCP Terraform's access control natively and securely.
